# 챕터 검수

기준 문서는 저장소 루트의 **`REVIEW_GUIDE_2026-09.pdf`**(결함 사례·심각도·이슈 양식)와 **`REVIEW_PLAN_2026-09.md`**(절차·라벨·이슈 구성)다. 이 스킬은 그 둘을 실제로 돌려 본 결과 — 특히 **무엇이 결함이 아닌지** — 를 담는다.

## 세 산출물, 각자 다른 것을 본다

```
노트북 ─┬─→ executed/ ─→ build_wikidocs.py ─→ pages/          (WikiDocs)
        └─→ notebook_to_tex.py ─→ book/chapters/*.tex ─→ pandoc ─→ .epub   (EPUB)
```

**두 갈래는 서로를 안 거친다.** pandoc 은 `pages/` 를 읽지 않는다. 그래서 "WikiDocs 에 없다"가 "EPUB 에도 없다"를 뜻하지 않는다 — **각 산출물에서 직접 확인해야 한다.** (실제로 이걸 확인 안 하고 이슈에 "EPUB 도 동일" 이라 썼다가 정정한 적이 있다. tex 에는 멀쩡히 있었다.)

## 0. 먼저 — 이 챕터에 이미 올라온 것을 읽는다

**검수를 시작하기 전에 반드시 한다.** 이 저장소는 챕터당 2-3명이 보고, 앞선 검수자가 이미 판정하거나 수정 방향을 합의해 둔 것이 있다.

```bash
gh issue list --search '"Ch 12" in:title' --state all --limit 60   # 챕터 이슈 + 결함 이슈
gh issue view 36 --comments                       # 챕터 검수 이슈: 다른 검수자의 PASS 기록·발견 목록
gh issue view <결함번호> --comments                # 결함마다 — 댓글에 수정 방향 합의가 있다
```

`in:title` 없이 검색하면 본문에 챕터 번호만 스친 무관한 이슈까지 딸려 온다.

`--state all` 이 중요하다. **닫힌 이슈에 설계 결정의 근거가 들어 있다.** 결함 아님으로 종결된 것도, 이미 한 번 재구성을 거친 것도 거기 있다. 예를 들어 Ch 12 의 "근소 우위" 서술은 닫힌 이슈 하나에서 나온 재구성 결과인데, 그걸 모르고 보면 이미 결론 난 논의를 다시 연다.

여기서 얻어야 할 것:

| 무엇 | 왜 |
|---|---|
| 이미 등록된 결함 (열림·닫힘) | 중복 등록 방지 |
| 결함 이슈 **댓글** | 수정 방향이 이미 합의됐을 수 있다. (a)/(b) 안 중 무엇을 왜 골랐는지가 댓글에만 있는 경우가 있다 |
| 챕터 이슈 댓글의 기준 커밋·EPUB build | 내 검수 대상 버전과 같은지. 다르면 앞선 PASS 는 무효다 (계획서 §8) |
| 이미 지나간 재검수 회차 | "한 번 봤으니 깨끗하다" 는 성립하지 않지만, 무엇을 이미 훑었는지는 알고 시작한다 |

> ⚠️ **읽되, 체크리스트로 삼지 않는다.** 계획서는 페어가 *각자 독립적으로* 보라고 한다 — 가이드가 든 사례 상당수가 "한 사람은 지나쳤지만 다른 사람이 잡은" 것이다. 남이 찾은 것을 확인하는 작업으로 바뀌면 그 사람이 놓친 것도 같이 놓친다. **이미 올라온 것은 중복 방지와 맥락 파악에만 쓰고, 훑는 범위는 스스로 정한다.**

## 순서 — 기계가 먼저, 사람은 마지막

사람은 린터도 스크립트도 못 보는 것(사실정확성·설명의 흐름)에만 시간을 쓴다.

```bash
# 1) 기계 검사 — 출력 개수 대조 · 변환 누락 · T4 제약 · 수치 vs 실측
python3 .claude/skills/chapter-review/scripts/check_chapter_review.py 12

# 2) 전자책 규칙 E1~E9
python3 .claude/skills/notebook-to-wikidocs/scripts/check_wikidocs_md.py pages/12-*.md

# 3) 사람이 산문을 읽는다
```

`check_chapter_review.py` 는 **위반**(고쳐야 함)과 **후보**(사람이 판단)를 나눈다. 후보를 자동으로 결함 처리하지 말 것 — 대부분 교육용 예시 표다.

## 결함이 아닌 것 — 가장 자주 틀리는 판단

**실행마다 값이 달라지는 것은 결함이 아니다.** 이게 이 저장소의 확립된 판정이다.

| 관측 | 판정 |
|---|---|
| 산문의 metric 이 실행본과 소수점 셋째 자리에서 다름 | **결함 아님** — 재실행마다 달라짐 |
| "약 12분" 인데 실측 37초 | **결함 아님** — 런타임·네트워크에 좌우됨 |
| 산문이 **재현 가능한 사실**을 틀림 (데이터셋 이름, 챕터 번호, API, 설정값) | **결함** |
| 코드에 고정된 것이 산문 설명과 다름 | **결함** — 재실행해도 안 사라짐 |

판단이 애매하면 가이드 4쪽: "이걸 모르고 읽은 학습자가 틀린 것을 배우는가?" 예 → 최소 Major. "따라 하다 막히는가?" 예 → Blocker.

**알려진 오탐 목록은 [references/known-false-positives.md](references/known-false-positives.md) 에 있다. 결함으로 올리기 전에 반드시 대조할 것** — 66M/67M, `변경점 한 가지 원칙`, `nvidia-smi` 게재, H2/H3 번호 관례 등 실제로 헛짚었던 것들이다.

## 사람이 봐야 하는 것

기계가 못 보는 세 가지다.

1. **출력을 눈으로 읽기** — 깨진 글자(`�`, `□`), 이상한 반복, `0.500` 처럼 딱 떨어지는 수치. 에러 없이 통과해도 결함일 수 있다.
2. **교차참조 역방향** — 노트북이 "부록 §6 참조" 라고 하면 **그 산출물에 §6 이 실재하는지** 연다. 노트북엔 있고 페이지엔 없는 경우가 실제 결함이었다. 절 번호로 가리키는 참조는 산출물마다 번호 체계가 달라 잘 깨진다.
3. **변경점 한 가지 원칙** — 직전 챕터 대비 축(모델/태스크/Loss)이 하나만 변했는가.

## 수정 경로 — 무엇이 무엇을 무효화하는가

| 고친 것 | 재실행 | 재변환 | 재빌드 | PASS 무효화 |
|---|---|---|---|---|
| 노트북 **마크다운 셀·주석** | 불필요 | 필요 | 필요 | WikiDocs·EPUB |
| 노트북 **코드 (동작 변경)** | **필요** | 필요 | 필요 | 세 산출물 전부 |
| `pages/*.md` **산문** | 불필요 | 불필요 | 불필요 | WikiDocs |

`pages/` 의 **코드 블록과 `▶ 실행 결과` 는 손대지 않는다** — `executed/` 가 단일 출처다. 숫자가 틀렸으면 산문을 실측에 맞추거나, 실행본이 틀렸으면 Notebook 결함으로 올려 재실행 경로를 탄다.

## 함정

**tex 재생성은 pandoc 버전에 묶여 있다.** `notebook_to_tex.py` 는 `-f gfm+tex_math_dollars` 로 pandoc 을 부르는데, **pandoc 3.x 에서 `$...$` 가 수식으로 파싱되지 않아 인라인 수식이 깨진다** (`\(\to\)` → `\$\textbackslash to\$`). 재생성 전에 반드시 **수정 전 소스로 먼저 생성해 커밋된 tex 와 일치하는지** 대조할 것. 다르면 그 pandoc 으로는 재생성하지 않는다.

**Colab 실행 없이 PASS 를 남기지 않는다.** 정적 검토와 `executed/` 대조로는 "조건부 보류" 까지만 쓸 수 있다. 가이드가 요구하는 것은 런타임 초기화 후 처음부터 끝까지 실행이다.

## 이슈 등록과 기록

결함 1건 = 이슈 1개. 양식·라벨·`gh` 명령·챕터 이슈 연결은 **[references/issue-workflow.md](references/issue-workflow.md)** 를 볼 것.

핵심만: `gh issue create` 는 챕터 이슈에 **댓글을 달지 않는다.** 본문에 `#36` 을 쓰면 타임라인에 교차참조 줄만 생긴다. 검수 결과 댓글은 `gh issue comment` 로 따로 남긴다.

## 흔한 실수

| 실수 | 결과 |
|---|---|
| 기존 이슈를 안 읽고 시작 | 이미 등록·판정된 것을 다시 올리고, 댓글에 있던 수정 방향 합의를 놓친다 |
| 기존 이슈를 체크리스트로 삼음 | 앞선 검수자가 놓친 것을 같이 놓친다 |
| 산문의 수치를 그대로 믿음 | `executed/` 와 대조해야 실측을 안다 |
| 한 산출물만 보고 "다른 데도 같다" 라고 씀 | 두 파이프라인은 갈라진다. 각각 확인 |
| 실행마다 달라지는 값을 결함으로 올림 | 노이즈. 위 판정표 참조 |
| 관례를 결함으로 올림 | 다른 챕터도 그런지 먼저 grep |
| 스크립트 후보를 그대로 이슈화 | 대부분 교육용 예시 표다 |
